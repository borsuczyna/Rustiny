# Rustiny milestone tracker

Status legend: `DONE` (criteria verified by a test or measurement), `PARTIAL`, `NOT STARTED`.
Only verified facts are recorded here.

## Milestone 0 - Foundation: DONE

- [x] Cargo workspace (`crates/rustiny-{core,profiler,vulkan,editor}`), pinned toolchain (`rust-toolchain.toml`), `rustfmt.toml`, workspace lints.
- [x] Logging (`tracing`, stderr + rotating file + in-editor ring buffer), panic hook that logs a backtrace.
- [x] Config system (`config.toml`: typed, `deny_unknown_fields`, range validation, 1 MiB parse limit, atomic save, corrupt file preserved as `.corrupt`).
- [x] Error handling (`RustinyError`, `VulkanError`, `RunError`), atomic writes, generational handles (`Pool<T>`).
- [x] CI workflow (`.github/workflows/ci.yml`), architecture docs, ADRs.
- [x] Definition of Done: `cargo build`, `cargo test --workspace`, `cargo clippy -D warnings` pass; the application starts.

## Milestone 1 - Window + Vulkan + ImGui: DONE, with one scoped-out item

- [x] Native window (winit 0.30), Vulkan instance/device/queues/allocator, swapchain with controlled recreation, frames in flight, dynamic rendering + synchronization2.
- [x] Dear ImGui (docking) with Vulkan backend; window resize; input events; error handling (device lost is reported, not ignored).
- [x] Dockspace with default editor layout, layout persisted in `layout.ini` and verified to be restored.
- [x] Validation layer + synchronization validation: **0 errors** in the basic scenario (asserted by `crates/rustiny-editor/tests/smoke.rs`).
- [x] GPU readback screenshots (`--screenshot`), used by the smoke test to prove real rendering.
- [x] Start-up: Vulkan instance created on a worker thread in parallel with the window. Measured start of `main` to ready: median ~1.0 s (943-1109 ms, n=6, one machine), down from 980-1300 ms. The < 1 s target is **borderline, not reliably met**; the rest is driver time (`vkCreateSwapchainKHR` ~0.4 s). Details: `docs/performance/M1_MEASUREMENTS.md`.
- [ ] **ImGui multi-viewport: not enabled.** The spec says "if it works stably". The backend's multi-viewport route needs a different frame protocol (frame tokens, per-viewport swapchains). It is deferred, not faked. See `docs/architecture/ADR-0003-multi-viewport-deferred.md`.

## Milestone 2 - Editor shell: PARTIAL (started)

Done: main menu (File/Window/Help), dock layout, Console (live, filtered, virtualised), Profiler panel, theme (dark/light), reset layout.
Real panels so far: Project, Hierarchy, Inspector and a Scene view (read-only, GPU-drawn boxes, Milestones 3-5). Not done: toolbar, keyboard shortcut manager, Game view (labelled placeholder), per-panel persistence of open/closed state across restarts.

## Milestone 3 - Asset database: PARTIAL (two slices)

Done (`crates/rustiny-assets`, 24 unit tests; editor end-to-end tests for opening a project and for live updates): Unity project detection, strict GUID type, `.meta` reader, read-only scan of `Assets/` into a flat depth-first index with GUID and path lookup, problem report (missing / orphan / invalid / duplicate-GUID / folder-flag mismatch / unreadable / symlink), `--project <path>` in the editor with the scan on a background thread and a real Project panel (tree, tooltips with GUID, importer and size, list of problems). Opening a project is verified not to modify it.
Live updates (second slice): `notify` file watcher on `Assets/` with a 300 ms debounce, rescans that reuse the `.meta` results of unchanged files (real project: 120-150 ms instead of 480-610 ms, index identical to a full scan, nothing re-read), at most one scan at a time, last good index kept if a refresh fails; see `docs/architecture/ADR-0004-file-watching.md`. Verified end to end: files added while the editor runs appear in the index.
Not done: patching the index per changed folder (a rescan still walks the whole tree), content hashing instead of size+mtime, re-import of changed assets, `.meta` creation for new assets, importer settings, `Packages/` and package resolution, import cache, any actual asset import (textures, meshes, ...), row virtualisation for very large expanded folders. Verified on one real Unity 6000.4 project (26 670 files, 398 folders, 27 066 `.meta` files): all parsed, 3 genuine problems reported (2 files without `.meta`, 1 folder flag mismatch), scan 0.47-0.63 s (n=4, warm OS cache; a first single-threaded version took 15.7 s, fixed by using directory-listing metadata, reading only the first 4 KiB of each `.meta` and reading them on 8 threads). With the Unity editor closed, a listing of all 53 764 files in `Assets/`, `ProjectSettings/` and `Packages/` (path, size, mtime) was identical before and after running the scan and the editor on it. Only that one project has been tried, so other `.meta` variants are still unverified. `cargo run --release -p rustiny-assets --example scan -- <project>` runs the scan from the command line.

## Milestone 4 - Scene model and Hierarchy: PARTIAL (first slice, read-only)

Done (`crates/rustiny-scene`, 41 unit tests; two editor end-to-end tests): streaming UnityYAML document reader and field extractor (`unity_yaml`), scene model (`GameObject`s and prefab instances as a forest with parents, sibling order, components by class ID, local transform, active/layer/tag), loader with issue reporting, `--scene <file.unity>` and double-click on a `.unity` in the Project panel, loading on a worker thread, real Hierarchy panel (tree, tooltips, problems list) and a read-only Inspector (flags, local transform, component type names; prefab source resolved to its asset name through the project index). Design and limits: `docs/architecture/ADR-0005-streaming-unityyaml-reader.md`.
Verified on the one real scene available (`SampleScene.unity`, 305 MB, Unity 6000.4): 212 704 documents, 20 597 game objects + 29 027 prefab instances = 49 624 hierarchy nodes, 12 roots, depth 8, 0 problems; counts equal to independent `grep` counts of the file. Load 0.67-0.80 s in a release build (n=6, warm cache), peak working set ~34 MiB (sampled, one run); inside the editor, next to the project scan, about 1 s. With the project and scene open, a fingerprint of every file under `Assets/`, `ProjectSettings/` and `Packages/` (path, size, mtime) and the scene's own size and mtime were identical before and after. `cargo run --release -p rustiny-scene --example scene -- <file.unity> [--tree N]` inspects a scene from the command line.
Not verified: the interactive parts (selecting a node, the Inspector contents, double-click to open) have no automated test and were only seen in a screenshot of the freshly opened scene; only that one real scene has been tried.
World transforms (parent matrices applied down the hierarchy, `rustiny_scene::math::Mat4`) are computed at load time; a prefab instance's local transform is assembled from the scene's overrides of its root transform (29 026 of 29 027 instances on the real scene; values the scene does not override use Unity's defaults because `.prefab` files are not read). World extent on the real scene is plausible (x -1842..2019, y -3..96, z -2737..2567, medians near the village).
Not done: component values (only types are listed), prefab contents and the other overrides (a prefab instance is one node, and its name can be the override of a nested object), prefab asset (`.prefab`) loading, scene editing or saving, selection in a 3D view, multi-scene, binary-serialized scenes (rejected with an error), Hierarchy row virtualisation (an expanded node with tens of thousands of children is drawn in full), search/filter, drag and drop.

## Milestone 5 - Scene view and rendering: PARTIAL (third slice: real FBX meshes with name-matched materials and albedo textures)

Done (`ui/panels/scene_view/`): free-fly camera (right mouse + W A S D / Q E, Shift faster, wheel dolly, `F` frame selection, `Home` frame all), ground grid with world axes, one marker per object at its world position (colour by game object / inactive / prefab instance), click to select (shared with Hierarchy and Inspector), selection ring with local axes and name, per-frame vertex budget (nearest 10 000 markers when more are in view). Camera maths and marker selection have unit tests (pinhole projection, near-plane clipping, left-handed basis, picking, budget); a headless Dear ImGui test injects real mouse and key events and checks clicking in the Hierarchy and the Scene view and flying with the right button held. Cost on the real scene (release build, 49 624 objects): 0.7 ms median / 1.3 ms worst per frame for projecting and choosing markers, 3.5 ms once per scene for framing.
That was the first slice (CPU markers in an ImGui draw list). It stays as the fallback when no GPU target exists (headless tests, or if creating the renderer fails); see ADR-0006.

**GPU scene pass (second slice, `crates/rustiny-render`, ADR-0007).** The Scene panel now shows an offscreen Vulkan image: every scene object is drawn as an instanced unit box placed by its world matrix (so position, rotation and scale are real), with depth testing (reverse-Z, infinite far plane), one directional light plus ambient, colour by kind (game object / prefab instance), inactive objects hidden unless selected, the selected object highlighted yellow, and a procedural ground grid with the world X/Z axes. WGSL shaders are translated to SPIR-V by `naga` in `build.rs` (no external shader compiler). Clicking picks the nearest box under the mouse (ray vs oriented box, falling back to the nearest marker for tiny or zero-scale objects); the selection ring, axes and name are still drawn as an overlay.
**The boxes are placeholders, not the models.** There is no mesh, material or texture import yet, so a scene shows as thousands of unit cubes scaled by the objects' transforms; no shadows, culling, LOD, transparency, skybox or post-processing exist. (Since the third slice an object is drawn only while it and all its parents are active.) Instances live in host-visible memory and are re-uploaded as a whole when a scene loads.
Verified: `rustiny-render` has 10 unit tests (box geometry, view-projection maths, push-constant layout) plus 5 headless GPU tests that render offscreen with Vulkan validation and synchronisation validation on and read pixels back (lit box colour and size, depth ordering independent of draw order, hidden vs selected instances, grid axes, resizing); they ran 3 times in a row without a failure or a skip on one machine (NVIDIA RTX 5050 Laptop, Vulkan 1.4). The editor checks that its CPU projection and the GPU matrix agree to 0.05 px on the same camera, and that box picking agrees with where a box is drawn; an end-to-end editor run with validation on opens a generated scene and requires at least one GPU pass and zero validation errors. On the real 49 624-object scene (debug-profile build, 1200x675 window, one machine, 3 runs): 9 GPU scene passes, 0 validation errors or warnings, and the GPU time of the pass measured with timestamp queries was 0.33-0.35 ms (the CPU cost of recording is recorded by the profiler as a `scene_pass` scope but was not measured separately). A panel resize re-points the UI texture, which waits for the GPU once, so resizes are debounced by 3 frames.
Not verified: how it looks or feels with a real mouse over a long session (only a screenshot of the framed scene was inspected; clicking boxes in the real editor has unit tests but no end-to-end test); other GPUs and drivers.
**Fifth slice, second stage: drawing the project's own shaders (`crates/rustiny-render/src/unity`, `crates/rustiny-editor/src/shaders`, ADR-0010).** Compiled passes are reflected, their descriptors merged by name into one set and patched with `rebind`; constant buffers (`UnityPerDraw`, `UnityPerMaterial`, camera/time/light globals) are filled by member name from the `.mat`, the camera and the instance matrices; textures, samplers, vertex inputs the mesh lacks and render state (blend, colour mask, reverse-Z depth) are provided. The editor's `ShaderHub` compiles on a worker and picks the pass and keywords from each material. Verified: GPU tests with validation on (matrix layout, frame values, blending, hidden instances, fallback to the native look), unit tests for `rebind`, material parsing, matrix maths and pass/keyword choice; real scene: 3 pass variants compiled, 0 rejected, 58 materials drawn with them in 5855 draws, 0 validation errors, scene pass 7.3 ms. Two bugs were found only by looking at the screenshot and fixed (a parser bug that dropped the program of any pass with `AlphaToMask[_Prop]`; `unity_LightData.z` was 0, so there was no direct light): afterwards 15 pass variants and 363 materials (14127 draws) use project shaders, roads and roofs are lit. **The terrain is still not drawn with its shader**: its tiles are prefab instances with a serialized `.asset` mesh and a material override, and none of `.prefab` expansion, `.asset` meshes, `MeshFilter`/`MeshRenderer` values or YAML textures is implemented. Limits: procedural instancing/storage buffers read zeros (the foliage shader renders black), no shadows/probes/depth textures, flat ambient, both faces drawn, no transparency sorting, no selection highlight on shader sections, no `CGPROGRAM`, not compared with Unity.

**Fifth slice, first stage: Unity shaders from their own HLSL (`crates/rustiny-shader`, ADR-0010).** A ShaderLab parser (properties, sub-shaders, passes, render state, `UsePass`, `HLSLINCLUDE`, pragmas), a package mirror so `#include "Packages/..."` resolves without touching the project, DXC compilation of a pass's HLSL to SPIR-V (Unity's HLSL dialect, keyword defines, hash-keyed cache) and a SPIR-V reflection reader (vertex inputs, constant buffers with member offsets, textures, samplers). Verified: 16 unit tests (parser, `UsePass`, mirror, a real DXC compile with caching, reflection of a known shader; the DXC ones skip when `dxc` is missing) and a report over the real project: 36 of 36 `.shader` files parse and 71 of 71 HLSL passes with a vertex and a fragment entry compile to SPIR-V and reflect with default keywords (4 `CGPROGRAM` passes, 6 passes without a vertex+fragment pragma pair, other keyword variants and compute shaders not attempted). Drawing followed (see the next paragraph).

**Fourth slice: URP Lit surfaces (ADR-0009).** Materials are drawn with a native implementation of URP Lit's inputs: normal maps (tangent frame from screen-space derivatives), metallic/smoothness (map or scalars), emission, Unlit, alpha clip, one directional light + ambient + Blinn-Phong specular. Each mesh section has a record in a storage buffer; a draw pushes its index; a section binds a descriptor set of three textures (albedo sRGB, normal and metallic-smoothness linear, 1x1 defaults while absent). PNG rows are now flipped to V-up (textures were upside down before). Verified: 20 render unit tests and 19 headless GPU tests with validation on (normal-map tilt toward/away from the light, matte vs metal vs metal-through-a-map, unlit and emission, 700 sections with distinct textures across several descriptor pools, material records starting over after `clear_meshes`), editor unit tests for shader property detection, PBR property mapping and row flipping; real scene (release, RTX 5050 Laptop): 3 787 models, 7 138 draws, 1 440 textures / 357 MB, 7.3 ms GPU per pass, 0 failures. Limits: not Unity's BRDF (Blinn-Phong, no environment map, no shadows), no occlusion/detail maps, custom shaders (LitNormalFade, tree/terrain/water shaders) still approximate or grey, no true transparency, the look was judged by eye and **not compared with Unity**.

**Third slice: real models, materials and textures (`crates/rustiny-model`, `crates/rustiny-render`, `crates/rustiny-editor/src/meshes`, ADR-0008).** Binary FBX models are read (14 unit tests; all 9 278 `.fbx` files of the real project import without error), converted to Unity's conventions and drawn instanced, one draw per material section. Prefab instances whose source is an `.fbx` are drawn as that model (highest `_LOD0`/no-suffix variant only); everything else stays a proxy box, and empty game objects keep a hidden box (visible when selected). Models and textures load on worker threads and are uploaded within a per-frame budget, so the scene opens at once and fills in. Materials: a model's material names are matched to `.mat` file names (tint, `_BaseMap`/`_MainTex` albedo, alpha clip), only for properties the material's shader declares. Albedo PNGs are decoded on workers, shrunk to at most 256 px, mipmapped and sampled with a trilinear repeat sampler (descriptor set per texture, copies recorded in the frame's commands, 8 MB per pass).
Verified: `rustiny-render` has 17 unit tests and 14 headless GPU tests (validation and synchronisation validation on, pixels read back): per-section tints, instancing and selection by object id, meshes arriving after their instances, replacement and clearing, texture sampling of known texels, tint x texture, alpha cutoff, a missing texture falling back to white and appearing later, rejection of inconsistent meshes/textures, and 700 textures of 256x256 streaming in over several passes; they passed 3 runs in a row. The editor has unit tests for the plan (LOD heuristic, hidden boxes, inactive parents), `.mat` matching and shader property detection, PNG decoding (RGBA/RGB/gray, shrinking) and the stream (failures reported, cancellation). The PNG decoder's mean colours were compared with Pillow's for all 3 023 PNGs of the project (no difference above 12/255 in any channel mean). Real scene (`SampleScene.unity`, release build, RTX 5050 Laptop, validation on): 3 787 models uploaded in about 1 s with 0 failures, 14.2 M triangles in 7 138 draw calls per pass, scene pass 7-8 ms GPU time, 0 validation errors or warnings; 8 140 of 10 887 material slots (75 %) matched a `.mat` by name; 1 184 textures requested, 1 184 uploaded, 0 failed, 275 MB of GPU texture memory.
Known limits: orientation and scale of the models were judged by eye (buildings upright, roads flat) and **not compared against Unity**; LOD selection is a file-name heuristic; material assignment is by name, not through the importer's remap table or the prefabs' renderer material lists, so 25 % of slots stay grey and some will have the wrong material; materials whose shader blends terrain layers are drawn grey (the blend is not evaluated); transparent materials are approximated by alpha testing; no shadows or lighting beyond one directional light (normal maps and metallic/smoothness were added in the fourth slice); textures are capped at 256 px and never evicted; `.prefab` assets are not expanded, so large prefab instances (buildings made of several models) are still single boxes; `MeshFilter`/`MeshRenderer` components are not read; models are flattened (no skins, animation or blend shapes); no frustum culling (GPU cost is currently 7-8 ms per pass at this scene size).
Not done in this milestone: `.prefab` expansion and component values, frustum culling, selection outline, translate/rotate/scale gizmos, Game view, multi-viewport, scene editing, GPU picking, an end-to-end test of clicking and flying in the real editor.

### URP frame, sky, scene lighting, faster loading (ADR-0012)

Done: frame order opaque -> skybox -> copy -> transparent; `_CameraOpaqueTexture` and `_CameraDepthTexture` are real copies; HDR (float16, linear) scene target with a final sRGB pass; Unity passes use clockwise front faces (`SV_IsFrontFace` was inverted, so the water drew its underside); exact `_ZBufferParams`, `unity_OrthoParams.w = 0`; sun, ambient (trilight SH) and reflection intensity read from the scene's `RenderSettings` and `Light`; the skybox material is compiled and drawn; project globals (`_GlobalDaylightVisibility`, wind, water) set to the authored scene's values; the package include mirror repairs missing files. Scene loading is parallel: prefab and model files are read on all cores and objects expanded in parallel, merged in scene order (real scene: planning 28 s -> about 1 s, same counts: 41 333 instances, 525 549 overrides, 40 without a target). Verified: GPU test for the camera textures, recomputed GPU blending tests, unit tests (settings/light parsing, SH, sun, parallel order); real scene by screenshot, 0 validation errors.
Not done: reflection probe cubemap, shadows, post-processing (tonemapping), sun colour temperature, tangents/vertex colours/UV1 on the GPU, transparency sorting, URP's own Lit shader (materials without a project shader still use the native approximation); never compared with Unity side by side.
